# illumio-ops v6 重建路線圖

> **Spec：** `docs/superpowers/specs/2026-10-24-illumio-ops-v6-rebuild-design.md`（2026-10-24 核可）。
> 本檔只定階段、順序、相依與驗收；**每個階段的詳細計畫輪到時才寫**（P1 已寫：
> `2026-10-24-v6-phase1-foundation.md`）。理由：同日寫好的多份計畫在依賴被改寫後會大量過期
> （v2 Phase 2D 半數死亡），v6 的後段依賴前段產物，提前寫等於寫兩次。

## 程式碼放置（全階段共用）

- 新程式放在 repo 根目錄的新套件 `illumio_ops/`（Python）與 `web/`（前端原始碼，建置輸出到
  `illumio_ops/web/static/`）；新測試放 `tests_v6/`；新腳本放 `scripts/v6/`；新 CI 為
  `.github/workflows/ci-v6.yml`；新依賴為 `requirements-v6.in`／`requirements-v6.lock`（py3.12 唯一鎖檔）。
- **舊的 `src/`、`tests/`、`scripts/` 在 P8 切換前完全不動**——測試機 .106 仍以 git checkout 跑 5.x。
- 每個階段在自己的分支（`feat/v6-p<N>-<slug>`）、獨立 worktree 開發，完成驗收後合入 main。
- 回收舊碼的方式：複製到新位置再改（`git mv` 不適用，舊碼要保持可執行到 P8），commit 訊息註明來源
  檔案與 5.x commit，以便追溯。

## 全階段硬性守門（P1 建立，之後每階段都要通過）

對應 spec §4.3 反目標，每條都是 `tests_v6/gates/` 下的一支測試，P1 寫好、之後只增不減：

1. **相依方向**：`illumio_ops.domain` 不得 import 任何 `illumio_ops` 其他子套件；`store`／`pce`／`settings`
   不得 import `services`／`web`／`jobs`；`services` 不得 import `web`。（AST 掃描）
2. **無 print**：`illumio_ops/` 內除 `rescue.py` 外不得出現 `print(`。（AST 掃描）
3. **每條 `/api` 路由都有契約**：註冊的 Flask 路由與契約登錄表一一對應。
4. **每條 `/api` 路由都有前端呼叫者**：契約登錄表的每個 operation id 都在 `web/src` 被引用（P1 起；
   P1 只有 PCE 連線與健康檢查兩條）。
5. **每個設定鍵都有讀者**：schema 的每個葉欄位在 `illumio_ops/`（schema 檔以外）至少被讀一次。
6. **每張表單一寫入者**：每張 SQLite 表在登錄表宣告擁有模組；對該表的 INSERT／UPDATE／DELETE
   只能出現在擁有模組。（AST＋字串掃描）
7. **路徑不依賴工作目錄**：`illumio_ops/` 內不得出現 `os.getcwd(`、`Path.cwd(`、以相對路徑字面值
   開檔。
8. **守門有效性**：每支守門測試附一個「注入違規後必須變紅」的自我測試。

   （`docs/superpowers/plans/YYYY-MM-DD-v6-phase<N>-<slug>.md`）。
3. 把 CI 的每道閘門列成清單，階段內每個任務之間親自跑。
