## 全階段硬性守門（P1 建立，之後每階段都要通過）

對應 spec §4.3 反目標，每條都是 `tests_v6/gates/` 下的一支測試，P1 寫好、之後只增不減：

1. **相依方向**：`illumio_ops.domain` 不得 import 任何 `illumio_ops` 其他子套件；`store`／`pce`／`settings`
   不得 import `services`／`web`／`jobs`；`services` 不得 import `web`。（AST 掃描）
2. **無 print**：`illumio_ops/` 內除 `rescue.py` 外不得出現 `print(`。（AST 掃描）
3. **每條 `/api` 路由都有契約**：註冊的 Flask 路由與契約登錄表一一對應。
4. **每條 `/api` 路由都有前端呼叫者**：契約登錄表的每個 operation id 都在 `web/src` 被引用（P1 起；
   P1 只有 PCE 連線與健康檢查兩條）。
5. **每個設定鍵都有讀者**：schema 的每個葉欄位在 `illumio_ops/`（schema 檔以外）至少被讀一次。
6. **每張表單一寫入者**：每張 SQLite 表在登錄表宣告擁有模組；對該表的 INSERT／UPDATE／DELETE
   只能出現在擁有模組。（AST＋字串掃描）
7. **路徑不依賴工作目錄**：`illumio_ops/` 內不得出現 `os.getcwd(`、`Path.cwd(`、以相對路徑字面值
   開檔。
8. **守門有效性**：每支守門測試附一個「注入違規後必須變紅」的自我測試。

## P4.5 允許流量的異常偵測（使用者方向 2026-10-26；設計見 spec §6.5.8，第一批待使用者挑選後寫計畫）

建議排在 P5 之前；第一批 A 同群偏離、B 量暴增、C 帳號新來源、D 程式異常、E 目錄／認證＋管理 port 三分類。下面是 E 的原始討論。SIEM 東西向流量分析指引隨 P7 交付。

### 原始討論：橫向移動偵測補強（P4 驗收時，2026-10-26）

LDAP、Kerberos、資料庫目前與 SSH／RDP／SMB 同屬「管理 port」：設了管理群組或環境 label 之後，「非管理群組使用管理
port」與「跨環境」會把每台網域成員連 DC 都標出來。建議：

```
遠端執行／控制  SSH RDP SMB RPC WinRM VNC TeamViewer Telnet → 扇出、非管理群組、跨環境、樞紐鏈（現有偵測器）
目錄／認證      88 389 636 3268/3269 464 9389(ADWS)       → 下列 1–5
資料庫          1433 3306 5432                            → 新連線、扇出、跨環境
```

1. 去錯地方：認證流量流向非目錄伺服器（偽 DC、relay）——P4 traffic 規則加目的排除即可做，需宣告 DC。
2. 從錯地方來：非受管來源、基準期沒連過 DC 的來源（新機器也會中，中等）。
3. 量不對：單一來源對 DC 的 LDAP／ADWS 連線數比自己 7 天基準暴增 N 倍（BloodHound／SharpHound 列舉），用 P4 增量表。
4. 誰發起不對：88／389 的發起程式不是 lsass／svchost（Rubeus、python、powershell），現有「非預期發起 process」加預設期望。
5. 接下來做什麼：目錄查詢暴增後 N 分鐘內同來源做 SMB／WinRM／RDP 扇出 → 以前兆加權升級。

報表（P5 橫向移動態勢）加一節「目錄與認證流量」：宣告與推論的目錄伺服器、流向非目錄伺服器的認證流量、每來源 LDAP
量與相對基準倍數、新來源、非預期發起程式、跨環境認證流量。lab 有可驗的流量（389：4 個來源對 1 台；88、3268、9389 都有）。
