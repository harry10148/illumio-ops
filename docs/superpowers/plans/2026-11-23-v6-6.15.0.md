## Task 1：規則排程只改 Draft，選項「時間到也 Provision」

現況（`illumio_ops/services/rule_schedules.py`）：每 5 分鐘 `tick` → `_check_one`：Rule Set 有任何未 Provision 變更（`pw.draft_pending`）就跳過；
否則 `_switch` 改 Draft 的 `enabled` 並 Provision 整個 Rule Set，失敗就 `revert`。建立／改計畫時 `_write_note` 寫備註並 Provision；刪除時清備註並 Provision。

**定案：**
1. 每個排程一個「時間到也 Provision」選項，**新排程預設關**。關＝只改 Draft，不 Provision；開＝現在的做法照舊。
2. 只改 Draft 的排程**只在開關時間點寫一次**：記住上次寫入的目標狀態（新欄位，例 `last_want`），desired 沒變就不再寫——有人在 PCE 上手動改回 Draft 不會被蓋掉。
   不因 Rule Set 有別人的未 Provision 變更而跳過（只改一個欄位，不會把別人的變更帶上線）。
3. **一個 Rule Set 只能有一種模式**：建立或改模式時，同一個 Rule Set（`pw.ruleset_of`）裡已有另一種模式的排程就拒絕，回明確的錯誤鍵（說出是哪個排程）。
4. 只改 Draft 的排程，備註也只寫進 Draft（建立、改計畫、刪除、到期清除都不 Provision）；要 Provision 的排程照舊。
5. 到期（expiry）在只改 Draft 模式：把 Draft 的 `enabled` 改成關（若不同）、清備註（Draft），刪除排程，紀錄寫明「只改 Draft，未 Provision」。

**既有排程：** migration 加欄位時，現有排程設成「要 Provision」（維持它們建立時的行為，不在升級時靜默改變正在跑的排程）；CHANGELOG 寫明。

**資料：** `store/migrations/` 新增一支（`provision`、`last_want`；如需要再加 Draft 目前值欄位供畫面顯示）。`store/rule_schedules.py` 跟著改；`move_pce` 照舊。

**畫面（`web/src/pages/**/RuleSchedules.tsx` 與相關元件）：** 建立與編輯都有「時間到也 Provision」勾選（預設不勾）並附一句說明（只改 Draft 時要有人 Provision 才生效）；
清單每列標出模式；只改 Draft 的排程顯示「Draft 已改、尚未 Provision」這類狀態時，要對得到資料（讀 Draft 與 active 的 `enabled`）。
概覽的「被跳過」計數只算要 Provision 的排程。執行紀錄的動作文字分出「已改 Draft」與「已 Provision」。

**API：** `ScheduleCreate`、`ScheduleEdit`、`ScheduleView` 加欄位；新錯誤 `mode_mixed`（409）。重產 contracts 與 API 參考。

**測試（失敗先行）：**
- 只改 Draft：時間點到 → Draft 改了、沒有 Provision 呼叫；下一輪 desired 沒變 → 不寫；手動把 Draft 改回 → 不被蓋回；Rule Set 有別人的未 Provision 變更 → 照樣寫 Draft。
- 要 Provision：既有測試全數照舊通過。
- 混用拒絕：同 Rule Set 已有另一模式 → 建立與改模式都 409；不同 Rule Set 可以。
- 備註：只改 Draft 的建立／刪除不呼叫 provision。
- 到期：只改 Draft 模式刪除排程且不 Provision。
- migration：舊列升級後 `provision` 為開。
- e2e：建立表單預設不勾；勾選後清單標出模式；混用時看到錯誤訊息。
- commit `feat(v6-schedules): schedules change the draft only, unless set to provision`。

**lab 實測（主對話，部署後）：** lab PCE 上挑一條測試規則建只改 Draft 的排程，`check_now` 後讀 Draft 與 active：Draft 變、active 不變；
接著只還原那個 Rule Set 的 Draft（`pw.revert(ruleset)`，不可用空 body 的全域還原），刪排程。
