# illumio-ops v6 介面重做：資安主控台（設計）

日期 2026-11-03。來源：使用者 2026-11-02～03 的對話與定案樣本。本文件是主規格
`2026-10-24-illumio-ops-v6-rebuild-design.md` 的介面部分修訂；兩者衝突時，介面以本文件為準，資料與偵測語意仍以主規格為準。

樣本畫布（定案版，明亮模式）：https://claude.ai/artifact/R5dksrNv5SN1rm2b31PJLH ，原始檔存於 repo
`docs/superpowers/specs/2026-11-03-v6-ui-samples/`（`Main`=樣本 01 … `Modes`=11，`Tpl*`=12–16，順序見 `canvas.json`）。樣本裡的數字、主機名稱都是示意；版面、資訊順序、
每張畫面要回答的問題以樣本為準，文字以本文件 §6 的規則為準。

## 1. 為什麼

使用者：「現在的 UI/UX 很像半成品，完全不像一個資安產品」。定位（使用者原話整理）：

- 給**沒有 SIEM 的客戶**：只透過 API 拿資料就能產生告警。
- 進階模式搭配本機資料（cache），做更進階的告警與報表。
- 從事件出發做**調查**，提供原廠 filter 和流量地圖做不到的東西。
- 整體看起來、用起來要像一個資安產品。

另外使用者要求把 5.x 的**規則排程**（依時間啟用／停用 PCE 規則）加回來（主規格 §6.5 原本列為 v6.0 不支援）。

## 2. 目標、非目標、反目標

**目標**
1. 打開就是資安主控台：首頁是告警，主線是「告警 → 偵測 → 調查 → 動作（隔離、標為已知、規則排程）」。
2. 資訊密度像維運工具：數字列、表格、狀態標籤；時間與數字用等寬字。參考舊版（`design/v2/tour/shots`）的密度與結構，不照抄。
3. 每個功能都標出需要哪種模式，基本模式下的進階功能看得到、說明開啟條件，不會消失。
4. 規則排程加回，語意沿用 5.x。
5. 報表統一版式：第一頁一句結論＋重點數字＋發現與行動表，後面是編號章節、判定依據、與前次比較。

**非目標**
- 深色模式（使用者 2026-11-03：「就做明亮模式就好」）。只有明亮模式，不提供切換。
- 改動偵測、收集、報表計算的語意；本案只改呈現，除非 §5.1 明列要補的資料。
- 規則排程的 cron 運算式（5.x 遷移來的仍暫停並寫明，同報表排程）。

**反目標**（做到了也算失敗）
- 畫面或報表出現程式算不出來的判斷或猜測意圖（使用者 2026-11-03 指出樣本的「其中 2 項會放寬資料庫存取」「通常是測試時留下的」）。見 §6。
- 對非受管物件出現隔離按鈕（使用者 2026-11-03）。
- 基本模式下進階功能直接消失、或顯示成「沒有資料」好像一切正常（主規格反目標 8）。
- 為了好看把數字或狀態做成裝飾（顏色只表達嚴重度與狀態）。

## 4. 各畫面要回答的問題

每張畫面的版面以樣本為準；這裡寫的是每張畫面必須回答的問題與資料來源。

### 4.1 告警（首頁，樣本 01）
- 現在有幾則嚴重／高／中、多少已歸組（標為已知）。依類型篩選：橫向移動、允許流量異常、事件、系統。
- 清單每列：時間、等級、標題、偵測器類型、來源 → 目的、通知結果（已送 N／失敗）。
- 右側詳情：時間軸（事件＋偵測）、「原廠查不到的」（同群先例、首次出現的程式或帳號等，取自偵測 summary）、通知紀錄；
  動作：開始調查（主要）、隔離（只對受管物件，§4.4）、標為已知。

### 4.2 偵測（樣本 02）
- 攻擊面數字：可觸及重要資產（含與上次差異）、樞紐、全部強制後剩下、跨環境、本週新偵測。
- 偵測器狀態清單：每個偵測器的狀態（正常 N／累積中 x/y 天／缺標籤／欄位覆蓋 n%／停用）與原因，連到調整門檻。
- 可觸及路徑與建議切點（現有暴露圖與切點演算法），「模擬強制後」「產生 deny 規則草稿」連到現有試算。
- 最近偵測表。

### 4.3 調查（樣本 03）
- 從告警帶條件進入（返回連結）。條件列：篩選、分組（最多兩層）、排名指標。
- 分組結果表，含「同群先例」欄。【修訂 2026-11-11，使用者 2026-11-10 同意】原「左：事件＋流量時間軸」不做。調查頁提供的是：
  條件列、每個維度一個單層排名的維度欄（點值加入條件）、分組結果表與明細表；事件與偵測的時間軸在告警詳情（§4.1），不在調查頁重畫。
- 寫明欄位覆蓋（帶程式／帳號的連線比例），分組只涵蓋有值的部分。
- 動作：存成報表章節、在 PCE 主控台開啟、隔離（§4.4）。

### 4.4 主機與隔離（樣本 04）
- 主機標頭：名稱、標籤、IP、OS、VEN 版本、enforcement 模式、是否已隔離。
- 重點數字、平常的樣子（30 天基準：常連目的、常用程式、常見帳號）與「這次不一樣的地方」（取自偵測）。
- **隔離只對清冊中的受管 workload**（現有 `services/quarantine.py` 的 `unmanaged`／`not_in_inventory` 判定）：
  - 非受管或不在清冊：不顯示隔離按鈕，改顯示原因。
  - idle 或 visibility 模式：可套標籤，但標示「不會生效」（現有 `no_enforcement`）。
  - 文字只寫事實：套了哪個標籤、原本的標籤、enforcement 模式；實際擋掉什麼取決於 PCE 的 Quarantine 規則集。

### 4.5 規則排程（樣本 05，新增）

語意沿用 5.x（`docs/legacy-5.x/guide/automation.md` §1）：
- 目標：已佈署（Active）的 Ruleset 或單一 Rule；目標有未佈署 Draft 時不能建立。
- 類型：**每週時段**（星期、起訖、時區；起 > 迄為跨午夜）與**到期停用**（到期時間）。
- 動作：時段內啟用，或時段內停用。
- 引擎每 5 分鐘計算每筆排程「此刻應啟用或停用」，與 PCE 即時狀態不同才切換並佈署；目標或其規則集有未佈署 Draft 時
  **本輪跳過**並記錄；目標在 PCE 被刪除時標為已刪除、不報錯中止其他排程；到期排程停用後移除。
- 建立時在規則 description 寫入固定英文的排程註記，刪除或到期時清除。
- 紀錄：每次切換寫入本機排程紀錄（畫面上的上次結果與執行紀錄）與 job 日誌；PCE 本身會為 provision 與規則修改留下 audit
  事件，這些事件經現有的 PCE audit 來源送 SIEM。**不新增 SIEM 來源**【判斷】。
- 使用主規格的**寫入用 API key**（與隔離同一把，選填）；沒有設定時規則排程頁反灰並寫明。這是 v6 第三種 PCE 寫入（主規格
  §6.5 原為兩種），主規格要同步修訂。
- 畫面：狀態數字（排程數、今日切換／失敗、本輪跳過、下次動作）、本週時間表、排程清單（目標、類型、時間、現在、上次結果）、
  新增排程側欄（含預覽句「一三五 18:00 停用並佈署，隔天 09:00 啟用並佈署」）。
- 權限：佈署權限不寫入就無法驗證（`pce/capabilities.py` 只管版本，不管角色），所以不另做探測；寫入用 key 沒設定時頁面
  反灰並寫明；PCE 拒絕（403 等）時把 PCE 的回應照實寫進該排程的上次結果與頁首，不顯示成功。【判斷 2026-11-03】
- 基本模式可用。
- 5.x `rule_schedules.json` 在升級時遷移為**暫停**的排程，由操作者逐筆啟用【使用者 2026-11-03 同意】。遷移器不連 PCE，
  所以遷移時不檢查目標是否存在；排程啟用後第一輪檢查找不到目標就標為已刪除（同上）。遷移報告列出每筆的目標與類型。
  只改遷移器（未來的 5.x 升級）；已升級的安裝不補匯入（.106 的 5.x 規則排程目標早已刪除，主規格 §2）。

### 4.6 基本模式下的首頁（樣本 06）
- 只有事件類告警；導覽上需要進階模式的項目淡化並標 ◆。
- 一個虛線框說明進階模式才有的三類功能、資源需求，連到「系統 › 模式與資料來源」。
- 說明基本模式的調查方式（即時向 PCE 查詢、查完即丟）。

### 4.7 報表（樣本 07）與排程寄送（樣本 08）
- 範本頁：16 型依「資安評估／流量分析／政策／維運與稽核」分欄，每張卡片：名稱、模式標記、排程摘要或份數、產生／排程。
  下方產生列（報表、期間、範圍、格式與語言、立即產生／排程寄送）與最近產出（**報表的一句結論**、類型、時間、寄送結果、動作）。
- 排程寄送頁：排程清單、寄送紀錄、編輯側欄（頻率、期間與範圍、收件人、信件內容、保留份數、立即寄一次）。
  信件主旨帶報表的一句結論。

### 4.8 SIEM 轉送（樣本 09）
- 每個目的地一張卡：狀態、端點、四種來源各自送到哪個時間、24 小時送出數、積壓、DLQ、最後錯誤、送測試訊息。
- 一筆 CEF 樣本與東西向分析指引（現有 P7 內容）。

### 4.9 告警規則與通知（樣本 10）
- 依類型篩選；每列：通知（送出／只記錄）、類型、名稱與狀態（冷卻中、累積中）、條件、排除、7 天觸發次數。
- 規則測試：用最近的真實事件或偵測比對，顯示命中哪些規則、會送到哪些通道。
- 右側詳情：偵測器、最低嚴重度、排除條件、通知與冷卻、標為已知的數量。

### 4.10 系統：模式與資料來源（樣本 11）
- 兩種模式並列：各能做什麼、資源需求；目前模式標示。
- 資料狀態：事件、流量、基準期、每小時活動、缺口。磁碟用量分段。

## 5. 模式的呈現

v6 內部有三種收集模式（主規格 §6.4：輕量、告警、完整）。介面上用使用者的說法呈現為兩種【判斷】：

| 介面名稱 | 內部模式 | 標記 |
|---|---|---|
| 基本模式 | 輕量 | ●（綠） |
| 進階模式 | 告警、完整（完整多保留原始流量供長期調查；「系統 › 模式與資料來源」可在兩者間選） | ◆（紫） |

每個功能的模式標記必須依主規格 §6.4 的表，**不得比實際更嚴格**：
- 流量型報表在基本模式可用（按需查詢），卡片標「按需查詢，較慢、受 PCE 保留期限制」，不標 ◆。
- 需要 ◆ 的只有：橫向移動偵測、允許流量異常、流量型告警、SIEM 的新連線與偵測事件、需要本機基準的報表段落與上期比較。

（樣本 07 把流量類報表都標成 ◆，是樣本的錯，以本節為準。）

### 5.1 要補的資料與計算（審查後定案，【判斷】）

| 項目 | 做法 | 模式 |
|---|---|---|
| 告警「未處理數」 | 期間內未標為已知（`grouped_annotation` 為空）的告警數；不新增「確認」狀態 | 全部 |
| 主機「平常的樣子」 | 從 `flow_rollup_daily`（保留 90 天，含發起程式與帳號）取近 30 天依連線數排名前 5 的目的、發起程式、帳號 | 進階；基本模式寫「需要進階模式」 |
| 主機「這次不一樣的地方」 | 直接列這台主機近 7 天偵測的 summary（首次出現的程式、帳號、同群偏離等） | 進階 |
| 調查表「同群先例」 | 只在分組含來源主機或來源群組時出現：該列的來源主機所屬群組（`peer_group_keys`），在查詢期間開始前的基準裡，有幾台**其他**成員連過同一目的簽章與 port（沿用 A 同群偏離的 `peer_seen` 讀取）。群組未達 `peer_min_group` 寫「群組太小」 | 進階；基本模式不顯示此欄並寫原因 |
| 告警規則「7 天觸發次數」 | `alerts` 依 rule_id 計數 | 全部 |
| 規則測試（反向） | 選一筆最近的事件或偵測，逐條規則評估（重用現有評估函式），列出命中的規則與其通道；不實際送出 | 全部 |
| 排程寄送「保留份數」 | 不新增；沿用全域 `reports.retention_days`，側欄只顯示 | — |
| 每型報表的一句結論 | `ReportDocument` 新增 `conclusion`（模板鍵＋參數）；16 型各定一句模板，模板清單列入驗收審查（§9） | 依報表 |
| 規則排程 | 新資料表與 job（§4.5） | 全部 |

畫面上做不出來的項目一律寫原因（需要進階模式、群組太小、欄位覆蓋不足），不拿掉欄位、不顯示 0。

## 6. 文字規則（反目標 1 的具體做法）

1. **每一句都對得到資料或固定規則**：報表標題、卡片摘要、告警詳情、偵測說明，都由程式以模板加上算出的值產生。
   不得出現推論對象語意（例：「資料庫」除非來自標籤）、猜測意圖（「通常是測試留下的」）、或沒有對應計算的建議。
2. **判定依據寫在旁邊**：每個風險等級、每張規則檢查卡片，都寫出判定條件（例：Policy Diff 的風險表，取自
   `domain/policy_diff.py` `_risk`）。
3. **「建議」只來自固定的動作表**：例如暴露圖算出的切點、就緒度算出的會被擋連線。沒有對應計算的就不寫建議。
4. 數字缺資料時寫原因（累積中、欄位覆蓋、缺口），不顯示 0。
5. 報表的一句結論是模板句：例「Draft 有 {n} 項變更尚未佈署：新增 {a}、修改 {m}、刪除 {d}；其中 {h} 項為高風險」。

## 7. 視覺

- 只有明亮模式。【修訂 2026-11-11】色票自 6.2.0 起是 5.x Direction D 的外觀（白與暖色面、文字 `#313638`、橘色強調 `#FF5500`），
  以 `web/src/styles/tokens.css` 為準；本節初版列的灰底 `#F4F6F8`、文字 `#111827`、主要動作藍 `#2563EB` 與嚴重度色碼已不用。
  不變的要求：對比須達 WCAG AA（4.5:1），顏色不單獨表達意思（同時有文字標籤）。
- 字型：JetBrains Mono（時間、數字、主機名稱、程式名）與 Montserrat（標題，6.2.0 起）隨前端打包內嵌（不得連外）。中文內文用系統字型，依序 Noto Sans TC、
  PingFang TC、Microsoft JhengHei【判斷 2026-11-03：中文網頁字型數 MB，現有 tokens 刻意不內嵌；報表 HTML 是單檔寄送，
  也無法內嵌中文字型，介面與報表一致用系統字型】。
- 主要動作用強調色（tokens 的 `--accent`）；破壞性動作（解除隔離、刪除）紅框。
- 中文用語依主規格 §6.2.1。

## 8. 報表統一版式（樣本 12–16）

- 淺色、A4 可列印；頂線顏色表示整份最高風險。輸出維持現有 HTML／XLSX／JSON／CSV，**不新增 PDF 檔**（離線安裝包不加
  headless 瀏覽器）；「列印」用瀏覽器列印 HTML，列印樣式處理分頁與重複表頭。樣本上的「下載 PDF」改為「列印」【判斷】。
- 第 1 頁：眉標（產品・報表名）、**一句結論（§6 模板）**、期間與來源、重點數字列（含與前次差異）、S01 發現與行動表
  （嚴重度標籤、行動、證據）、資料涵蓋說明。
- 之後：章節列（00 摘要、01 發現…），編號章節；規則檢查卡片（標籤、判定依據、算出的數字；有對應計算才有建議）；與前次比較表。
- 與前次比較只在主規格 §6.4 允許的報表與模式出現；不能比時寫明原因。
- 長內容：表格超過一頁自動分頁並重複表頭；單格過長換行，不截斷（專案規則）。

## 9. 驗收

- 每張畫面以真資料（.106 lab、.135 NFR）在 1280 與 760 寬度用 Playwright 截圖檢查：無水平溢出、無未翻譯鍵、無殘留 `{}`。
- 兩種模式各走一遍：基本模式下進階功能顯示說明而非空白。
- 隔離：對非受管與不在清冊的目標不出現按鈕；idle／visibility 標示不會生效。
- 規則排程：lab 上建一筆每週時段與一筆到期停用，跨過切換點各驗證一次 PCE 狀態與佈署；有 Draft 時跳過並記錄。
  （lab PCE 寫入由使用者用 `!` 執行，或使用者事先授權。）
- 報表：每型以真資料重產，逐頁檢查截斷與溢出；抽查每一句結論都對得到資料。
- 文字規則：所有模板句與判定依據列成清單審一次，沒有推論句。
