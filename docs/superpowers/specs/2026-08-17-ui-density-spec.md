# UI 資訊層級規範（Phase 2A-R）

2026-08-17。適用於 `src/static/js/v2/` 的全部 18 條路由。

## 為什麼要有這份東西

Phase 1 的 mockup 是**設計審查用的產物**，它的職責是證明自己忠實對應舊版，
所以每個面板都在展示自己的推導過程：資料從哪個端點來、對應哪個欄位、
舊版怎麼做、這裡為什麼不一樣。Phase 2A 忠實移植了那個語氣。

結果是一個「解釋自己」的介面，而不是一個「讓人做事」的介面。
使用者回饋：太密集、太工程師。

這份規範定義的是**資訊層級**，不是視覺樣式——換句話說，改的是
「哪些東西該出現在畫面上、以什麼順序」，而不只是措辭。

## 六條規則

**R1 — 每頁先回答一個問題。**
頁面最上方是**結論**（一句話或一個數字＋狀態），不是資料表。
資料表是支撐結論的證據，位置在結論之後。

**R2 — 三層，第三層預設收起。**
結論 → 需要注意的項目 → 全部明細。
「全部明細」預設不展開。一個運作正常的系統不需要把 14 列資料攤在使用者眼前。

**R3 — 正常狀態要安靜。（只適用於「狀況頁」，見下方原型）**
沒有異常時，該區塊只佔一行。異常才展開細節、才用顏色。
現況相反：14 個排程全部正常，卻佔滿整個畫面。

**這條不適用於設定頁**——使用者是來看設定值的，值本身就是內容，
把它收起來是幫倒忙。誤用這條規則會把「維運工具」變成「儀表板」。

**R4 — 技術識別字不上畫面。**
API 端點、內部欄位名、路由 hash、原始 JSON、程式碼識別字一律移除。
維運人員需要對帳時，走「說明」或開發者模式，不是預設畫面。
（本規則推翻 T12c 期間「來源標籤是設計慣例、應保留」的裁決。）

**R5 — 說明文字最多一句。**
超過一句就收進可展開的「說明」。
現況有整段落的技術說明釘在頁面底部。

**R6 — 領域詞彙保留，實作詞彙移除。**
`workload`、`ruleset`、`enforcement`、`PCE`、`VEN` 是使用者本來就在用的詞，留著。
`href`、`provision_state`、`last_status`、`job_health` 是實作細節，換掉。
判準：**這個詞出現在 Illumio 的產品介面上嗎？**

## 執行時的硬性要求

- **每一頁的資料模型都要從原始碼讀起**，不能從 mockup 或文件推。
  （本專案已有前例：UI 重構因為從文件出發而連續遺漏，被喊停。）
  判斷「什麼是結論」必須基於後端實際算出什麼、以及什麼情況下會出錯。
- 每頁改完要**在測試機上看畫面**，不能只看測試綠燈。
  這一輪最有價值的三個發現沒有一個是閘門抓到的。
- 既有的 `data-cov` 覆蓋錨點（102 個）是移植完整性的證據，
  改版時若要移除任何一個，必須在計畫裡逐一說明理由。

## 三種頁面原型

規則不能一體適用。從各區實際載入的資料集推出來，18 條路由分成三類：

| 原型 | 回答的問題 | 路由 | R3 是否適用 |
| --- | --- | --- | --- |
| **狀況頁** | 有沒有問題？該做什麼？ | `#/overview`、`#/automation/jobs`、`#/alerting/ops` | ✅ 適用 |
| **設定頁** | 目前設定是什麼？我要改什麼？ | `#/system/*`（八頁）、`#/alerting/rules`、`#/automation/rules`、`#/automation/reports` | ❌ 不適用 |
| **工作頁** | 我要查一件事／產一份東西 | `#/investigate/*`（三頁）、`#/reports` | 部分（結果區適用，輸入區不適用） |

判斷依據取自各區宣告的資料集，例如 `system.mjs` 已經把
**設定（strict，載入失敗就沒有表單可畫）**與**遙測（soft，失敗只降級）**分開，
這個既有的區分正好對應原型邊界，不是我另外發明的。

最需要處理的是 `#/overview`：它載入 14 組資料，是唯一的著陸頁，也是密度問題最重的一頁。
它同時也是風險最高的一頁——改壞了使用者第一眼就看到。**排在最後做，不是最先。**

## 現況樣本（逐字取自測試機上的實際畫面）

這些是使用者說「太密集、太工程師」時看到的東西。列在這裡是因為
規則若脫離實例，很容易變成套話。

- 每個頁面標題旁邊印著路由：`自動化 #/automation/rules`
- 面板角落的端點標籤：`GET /api/rule_scheduler/status`、
  `GET /api/dashboard/overview → job_health[]`
- 卡片下方的說明是後端欄位路徑：「`dashboard_overview.job_health` 的全部項目」
- 圖表下方的來源標記：`timeline_24h`
- 敘述句中間的實作細節：「後端固定回 `requires_restart:true`，且每次儲存成功
  都會叫出這條橫幅」、「`last_status` 為 error 時一律以紅色呈現」
- 安全設定頁把送出的 request body 以原始 JSON 攤在畫面上
- SIEM 測試面板逐條教學回應欄位：`ok` / `latency_ms` / `error` 各代表什麼
- 自動化頁底兩大段落，講對帳三態與 href 的組成結構
- Job 健康頁：14 個排程全部正常，卻用四張統計卡＋14 列表格＋節拍進度條佔滿整頁

## 執行時會一直撞到的東西：測試綁在可見裝飾上

第一刀就撞到了。移除頁面標題旁的路由字樣（`自動化 #/automation/rules`）時發現
**20 個 e2e 測試把「頁面已切換」的訊號綁在那個 `<code>` 元素上**
（`page.wait_for_selector("code:text-is('#/reports')")`）。

拿掉裝飾 → 測試全紅。這不是測試寫錯，是耦合錯了：**測試不該依賴使用者看得到的裝飾**，
因為那正是改版要動的東西。

處置：頁首改帶 `data-route` 屬性當語意掛勾，測試等屬性而非等文字。
**這個模式會在整個改版過程中重複出現**（表格欄位、面板標題、說明文字都可能是某個測試的
定位點），所以「把測試搬到語意掛勾」是這個階段的既定工作項，不是意外。
估算工時要把它算進去。

## 第一個示範：`#/automation/jobs`（狀況頁）

選它當第一頁的理由：範圍小、自成一體、資料模型單純（後端已經把 `level` 算成
error/warn/ok 三態），而且它現在正好是「全部正常卻佔滿整頁」的最極端例子。

**現在**：一段開場白 → 四張統計卡（各帶一句註解）→ 資料時間 →
一段 level 判定說明 → 篩選列＋端點標籤 → 14 列表格（5 欄，含節拍進度條）→
頁底兩段說明。

**改成**：

```
排程健康                                            [狀態徽章]
────────────────────────────────────────────────────────────
全部排程運作正常。資料截至 17:50:49。

  ⌄ 查看全部 14 個排程
  ⌄ 說明
```

有異常時，結論行換成需要注意的項目本身：

```
排程健康                                          2 個需要注意
────────────────────────────────────────────────────────────
siem_dispatch        上次執行失敗              11 秒前
pce_cache_archive    已逾期（間隔 24 小時）     2 天前

  ⌄ 查看全部 14 個排程
  ⌄ 說明
```

對照六條規則：

- R1：結論是「有沒有排程出問題」，不是統計表
- R2：三層＝結論／需要注意的／全部明細，第三層是現有的表格，收起來
- R3：正常時整頁一行
- R4：移除端點標籤、移除卡片註解裡的 `dashboard_overview.job_health`
- R5：level 判定、節拍條、歷史紀錄三段說明收進「說明」——**不刪掉**
- R6：`job_id` 這個欄位標題換成「排程」；`last_status` 換成「狀態」

**必須保留**：`AU-13` 覆蓋錨點、指令面板的 `au:jobs-bad`（改成展開全部清單並
定位到異常項）、teardown 註冊位置（在第一個 await 之前）。

## 字級尺標本身就是問題的一部分（實作第一頁時發現）

`src/static/css/v2/tokens.css` 目前的尺標：

```
--fs-micro:  9.5px   欄位標題、eyebrow
--fs-mini:  10.5px   meta、說明文字
--fs-body:  11.5px   表格儲存格、清單列
--fs-ui:      13px   基準內文
```

**維運人員一整天盯著的表格內文是 11.5px，說明文字 10.5px。**
這不是「講話方式」的問題，是尺標的問題——結構調整完，字還是一樣小。

處置：**獨立成一步做**，不混進結構示範。理由是它一動 18 頁同時變，
必須逐頁看過才知道有沒有把版面撐破；跟結構改動混在一起會分不清是誰造成的。
順序：先做完幾頁的結構示範 → 調尺標 → 全部重看一次。
