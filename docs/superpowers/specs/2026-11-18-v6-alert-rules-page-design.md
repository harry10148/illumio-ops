# 告警規則頁改版：每條規則都是「盯什麼＋條件＋門檻＋告警方式」

日期：2026-11-18 ｜ 狀態：使用者審過設計文件並核可（「ok繼續」）
樣張：https://claude.ai/artifact/St3pKVr16tY1LuTVLdXomL （第 4 個版本；事件目錄是程式裡真的 294 種與中文說明，規則與活動數字是假的）
前一份規格：`docs/superpowers/specs/2026-11-11-v6-purpose-led-ui-design.md` §10（第 4 段：情境清單＋短表單，6.11.0 交付）。
本文件取代 §10 的情境清單與短表單；§10 的「每條規則開了存回不變」的要求照舊。

標記：【使用者】使用者說的；【樣張】使用者看過樣張並同意；【判斷】我的決定，使用者沒有明確表示，讀的時候請特別留意。

## 1. 為什麼

使用者原話：

- 新增告警規則「不直覺」，「會有種找不到和不知道該怎麼設定的感覺，還有感覺有一堆東西」【使用者】。
- 「還有很多內建規則我看不懂他到底在做什麼，還有自定義規則怎麼好像少了流量驅動的？」【使用者】
- 「我的概念應該是設定告警就要像是一般的產品，針對某些事件等級和條件設定，或是某些 Ip 連線數量或是流量或是 allow/deny，
  只是有個內建規則會自動帶入參數」【使用者】

對照程式找到的原因：

- 新增頁（`ScenarioList.tsx`）先列 41 個情境，其中 29 個已有內建規則；使用者要先懂「情境」才找得到表單。
- 內建規則和自訂規則看起來是兩種東西：內建的只有名稱，自訂的要另外找表單；同一種規則有三種表單（情境短表單、完整表單、編輯）。
- 規則清單（`Rules.tsx`）是一張平的表，看不出每條規則盯哪些事件或哪些連線。
- 後端早就是使用者要的形狀：事件規則有事件類型（可為 `*`）、事件等級、結果（成功／失敗）、門檻；流量規則有來源、目的（IP、網段、標籤、
  IP 清單）、埠、政策判定（Allowed／Potentially Blocked／Blocked）、連線數／速率／傳輸量。問題只在畫面。

## 2. 目標、非目標、反目標

**目標**

1. 一張事件規則表、一張流量規則表；內建和自訂的放在一起，欄位一樣：名稱、條件、門檻、嚴重度、狀態【樣張】。
2. 只有**一個**規則表單，新增和編輯都用它，內建規則也用它【使用者】【樣張】。
3. 表單分四步：盯什麼（PCE 事件／流量）→ 條件 → 門檻 → 告警方式【樣張】。
4. 新增時可以「從範本帶入」：範本就是內建規則的參數，選了把表單填好，附一句說明這條在防什麼【使用者】【樣張】。
5. 挑事件有分類、搜尋、動作篩選、同資源分組全勾【使用者問「是不是要有更好的分類篩選機制」】【樣張】。

**非目標**

- 偵測規則（橫向移動 3、異常偵測 9）與系統檢查（6）不是「條件＋門檻」，另外設計【使用者：「你的特殊規則那就是另外要想的」】。
  這次在頁面上原樣列出（§4.6），編輯仍用現在的完整表單。
- 不改規則的資料模型、評估邏輯、內建規則包的內容與預設值。內建規則照現在安裝後就在跑【使用者選 A】。
- 不加每條規則各自的通知管道（管道是全域設定）。
- 不改告警頁、調查頁、偵測設定頁。

**反目標**（做到了也算失敗）

- 打開一條既有規則再存回去，任何欄位被改掉或清掉（例：樣式型的事件類型、`!info` 這種事件等級、流量條件的排除與程序欄位）。
  6.11.0 的「每條規則開了存回不變」測試要搬到新表單照舊通過。
- 有任何一條規則在新頁上找不到。
- 畫面上寫了算不出來的話（[[ui-text-must-be-computable]]）。
- 舊頁有的資訊或動作不見：上次觸發、7 天次數、已知次數、冷卻／頻率限制擋下次數、暫緩中與重設、資料狀態、評估一次、內建規則包
  （補上缺的／全部重設）、告警保留天數、規則試算（RuleTest）、通知管道那一行、試算最近 24 小時、刪除；
  清單上完整的條件（每一筆欄位比對 `path = pattern`、排除條件）；21 種偵測各自的說明與備註（`scn_det_*`）、從一種偵測開始建規則。

## 3. 現況（6.12.5）

```
/alert-rules            RulesAndChannels：分頁「規則」｜「通知管道」
  規則分頁               Rules（embedded）：評估一次、新增按鈕、內建規則包（補上缺的／全部重設）、
                         類型篩選、平表（名稱、類型、條件、排除、啟用、通知、上次、7 天、已知、狀態）、保留天數
                         ＋ RuleTest
/alerts/rules/new       ScenarioList：4 組 41 個情境
/alerts/rules/new?scenario=<組>:<id>   短表單＋進階
/alerts/rules/new?form=full            完整表單（任何類型）
/alerts/rules/:id       編輯既有規則（完整表單）
```

規則欄位（`domain/alertrules.py`）：共同有 `enabled`、`notify`、`severity`（None＝依事件或依偵測）、`cooldown_minutes`、`throttle`、`pack_key`、`name`
（沒有 `pack_key` 時必填）。事件規則：`event_types`（至少一個；可為確切類型、`a|b`、`*`、正規表示式）、`status`、`event_severity`、`match_fields`、
`threshold`（每次／累積）、`threshold_count`、`window_minutes`（1–1440）。流量規則：`traffic`（`threshold_connections`）、`bandwidth`（`threshold_mbps`）、
`volume`（`threshold_mb`），共用 `condition: FlowCondition` 與 `window_minutes`（10–1440）。

PCE 事件的 `severity` 只有 `info`、`warning`、`err`；`status` 是 `success`、`failure` 或沒有（原廠 REST API 25.2／26.1，microseg-kb 查證）。
事件目錄（`domain/event_catalog.py`）294 種、11 類；標 `status_filter` 的 12 種、標 `severity_filter` 的 11 種（會有不只一種結果或等級）。

## 4. 設計

### 4.1 頁面【樣張】

```
告警規則                                        [搜尋名稱、事件類型、IP…] [＋新增規則]
設定在什麼條件下產生告警。內建規則已經在跑，可以改參數；也可以從內建範本帶入參數，另建一條。
事件規則 17 · 流量規則 3 · 通知中 18 · 只記錄 2 · 最近 7 天觸發 125 次        [評估一次] [內建規則 ▾]
┌ 新增／編輯表單（按「新增規則」或某列的「編輯」才出現，§4.3）┐
└──────────────────────────────────────────────┘
事件規則   盯 PCE 送出的事件
  名稱 [內建]          條件                          門檻            嚴重度  狀態                 編輯
  上次 3 小時前·7 天 4 次
  登入失敗 [內建]      事件 user.sign_in、user.login · 只算失敗   10 分鐘內 ≥ 5 次  依事件  [停用|只記錄|通知]  編輯
流量規則   盯收進來的連線紀錄
  大量被擋流量 [內建]  來源 任何 → 目的 任何 · 判定 被擋   10 分鐘內連線數 ≥ 25 條  中  …
偵測與系統檢查（§4.6）
規則試算（現有 RuleTest，原樣）
告警保留天數（現有，原樣）
```

- 頁首計數全部由規則清單算出，三類都算：「事件規則 n · 流量規則 n · 偵測與系統 n · 通知中 n · 只記錄 n · 停用 n」【判斷】。「內建規則」選單收原本的「補上缺的／全部重設」；`pack_missing > 0` 時頁首另出一行提示並可直接補上【判斷】。
- 「通知管道」分頁不動。
- 舊頁的類型篩選拿掉，由兩張表與搜尋取代。

### 4.2 規則表

**歸屬**：`type=event` → 事件規則表；`traffic`、`bandwidth`、`volume` → 流量規則表；`lateral`、`system` → §4.6。由欄位決定，每條剛好出現一次（測試守住）。

**排序**：內建規則照 `best_practice_rules()` 的順序在前，自訂規則照設定檔裡的順序在後【判斷】。

**一列**：

| 欄 | 內容 |
|---|---|
| 名稱 | `display_name`；內建規則加「內建」小標；內建規則有任何欄位（`id`、`pack_key`、`enabled`、`notify`、`name` 除外）和 `pack_rules` 不同時，再加「和預設不同」——與「還原成內建預設」按鈕用同一個判斷【判斷：不寫「已改過」，因為從 5.x 搬來的規則本來就可能不同，沒人在 v6 改過】。名稱下一行是活動（見下）。 |
| 條件 | 事件：「事件 `類型`、`類型`」（`*` 寫「全部」），事件等級不是全部時加「等級 資訊、錯誤」，結果不是全部時加「只算成功／只算失敗」，每一筆欄位比對寫出 `path = pattern`。流量：「來源 … → 目的 …」，有埠時加埠，「判定 …」（沒勾寫「任何」），其餘有值的條件全部列出（同現有 `included()`）；有排除時第二行「不含：…」（現有 `exclusionSummary`）。IP 清單與標籤群組寫名稱（用 `condition_choices` 查；查不到才寫數量）。全部由欄位算出，放在 `ruleSummary.ts`。**不縮寫成「另有條件」**：舊表的條件與排除欄寫得出的東西這裡都要寫得出。 |
| 門檻 | 事件：`threshold=count` 寫「`{window}` 分鐘內 ≥ `{n}` 次」；`immediate` 且 `threshold_count=1` 寫「每次發生」；`immediate` 且大於 1 寫「每次檢查同一台主機 ≥ `{n}` 筆」（`alerting.py:312-321`：依主機分組，沒有主機時依事件類型）。流量：「`{window}` 分鐘內連線數 ≥ `{n}` 條」／「… 速率 ≥ `{n}` Mbps」／「… 傳輸量 ≥ `{n}` MB」。 |
| 嚴重度 | 固定值，或「依事件」。 |
| 狀態 | 三段切換「停用｜只記錄｜通知」，對應 `enabled=false`／`enabled=true, notify=false`／`enabled=true, notify=true`。切到停用不改 `notify`。用現有 `alert_rules.update` 送整條規則、帶 `revision`（同現在的 `toggle()`）。存檔中、存好、存失敗三種狀態照現在的開關（`data-state`）：失敗時切回原來那段並寫出原因（`test_ui_controls_e2e.py:74`）【判斷：兩個布林在舊頁是兩個開關，三態比較好懂，見 [[phase2c-cli-delivered]]】。 |
| 編輯 | 在頁面上方打開表單（§4.3）。 |

**活動**（名稱下一行，現有欄位原樣搬過來）：上次觸發（`last_fired_at` 是保留中的告警裡最近的一筆，不限 7 天；沒有時寫「沒有觸發紀錄」）、`fired_7d`、`known_7d`（大於 0 才寫）、
冷卻與頻率限制擋下的次數（`suppressed_cooldown + suppressed_throttle`，大於 0 才寫，同 `Rules.tsx:144`）、`held`（暫緩原因與到期時間，附「重設」與確認）、
`last_status`（不是 `ok` 才寫）【判斷：樣張只畫了前兩項，其餘是舊頁有、不能不見的】。

窄螢幕（≤ 860px）每列改成兩行：名稱＋編輯一行，條件、門檻、嚴重度、狀態往下排【樣張】。

### 4.3 規則表單【樣張】

一個表單元件，在頁面上方展開（一次一個）。新增時標題「新增規則」、按鈕「建立規則」；編輯時標題「編輯：{名稱}」、按鈕「儲存」。
網址帶狀態，可以直接連、上一頁可以關：`/alert-rules?rule=new`、`/alert-rules?rule=new&template=<pack_key>`、`/alert-rules?rule=<id>`【判斷】。
切到「通知管道」分頁會關掉表單（`RulesAndChannels.tsx` 的 `pick()` 清掉網址參數）；表單有改動時先確認。
表單打開時，頁首的「＋新增規則」改成次要按鈕，畫面上只有一個主要按鈕（`ui_rules.py` 的 `one_primary`）。

```
從範本帶入  [（不用範本，從空白開始）▾]           ← 只在新增時出現
            有人登入 PCE 失敗；短時間內很多次，可能有人在猜密碼。下面的參數已照內建規則填好。
1 盯什麼    (PCE 事件) (流量)
2 條件      事件：§4.4      流量：§4.5
3 門檻      事件：(每次發生就告警) (累積次數) → [10] 分鐘內發生 ≥ [5] 次
            流量：(連線數) (速率) (傳輸量) → 往回看 [10] 分鐘，符合條件的連線數 ≥ [25] 條
                  往回看的時間最少 10 分鐘（流量最快每 10 分鐘收一次）。
4 告警方式  名稱 [必填]   嚴重度 [跟事件等級▾]   狀態 [停用|只記錄|通知]
            ▸ 冷卻時間、頻率限制
            通知會送到：Email、Webhook。改通知管道
[還原成內建預設]                       [試算最近 24 小時] [取消] [建立規則]
```

**範本**

- 範本清單＝`alert_rules.pack_rules` 裡 `type` 是 `event` 或 `traffic` 的 17 條，分「事件」「流量」兩組。偵測與系統檢查不列（非目標）。
- 選了範本：除了 `id`、`pack_key`（設成 null）之外的欄位全部換成那條內建規則的值；名稱＝內建名稱加「（複本）」；狀態＝通知【判斷】。
  表單已經有改動時先確認「會蓋掉目前填的內容」【判斷】。帶入範本與「還原成內建預設」都要讓輸入框重新掛載（有些輸入框只在掛載時讀值：
  `ConditionEditor` 的 `defaultValue`、`RuleEditor.tsx:633` 的欄位比對框）。
- 範本下方一句「這條在防什麼」：17 句新文字（§5）。編輯內建規則時，同一句顯示在表單標題下【判斷：這是回應「內建規則看不懂」；
  列上已經有確切條件，這句放在表單裡】。

**盯什麼**：「PCE 事件」對應 `event`；「流量」對應 `traffic`／`bandwidth`／`volume`，由門檻的算法決定。編輯既有規則時這一步不能改【判斷：
換類型等於另一條規則；要換就新增】。

**門檻**

- 事件：每次發生＝`threshold=immediate`；累積次數＝`count`，`threshold_count`、`window_minutes`。
  選「每次發生」時下面多一句「同一次檢查裡，同一台主機達 [1] 筆才告警」（`threshold_count`，預設 1；`alerting.py:312-321` 依主機分組，
  沒有主機時依事件類型）。從「累積次數」切回「每次發生」時把 `threshold_count` 設回 1（同現在 `RuleEditor.tsx:491`）。
  `immediate` 時 `window_minutes` 不顯示、原值保留。
- 流量：三種算法對應 `traffic`、`bandwidth`、`volume`；切換算法時 `type` 跟著換，舊類型的門檻欄位拿掉、換上新類型的門檻欄位
  （規則不接受多餘欄位，`alertrules.py:25` `extra="forbid"`）；條件保留，視窗與門檻換成該類型 `blank()` 的預設，除非使用者已經改過。
  句子寫「往回看 N 分鐘」（`window_minutes` 是往回看的時間，不是檢查間隔）。連線數附現有 `rule_traffic_hint`；速率寫「任何一條連線的速率 ≥ N Mbps」、
  傳輸量寫「這些連線合計 ≥ N MB」，附現有 `rule_bytes_hint` 與 `scn_flow_bandwidth_notes`／`scn_flow_volume_notes`（說明哪些連線不計，這兩組文字留著）。

**告警方式**

- 名稱：自訂規則必填；內建規則可以空白（顯示內建名稱，placeholder 寫出來）。
- 嚴重度：事件規則多一個「跟事件等級」（`severity=None`），流量規則必選。
- 狀態：新規則預設「通知」【判斷：自己建就是要收到】。
- 進階（摺起來）：冷卻、頻率限制。現值和該類型 `blank()`（內建規則：`pack_rules`）不同時預設展開。
- 所有摺起來的區塊（這裡、§4.4、§4.5 的「更多條件」）在伺服器回報欄位錯誤、錯誤欄位在裡面時自動展開（同現在 `RuleEditor.tsx:392`）。
- 通知管道那一行：現有的 `notify-channels` 原樣。

**按鈕**

- 「還原成內建預設」：只在編輯內建規則、而且有欄位和 `pack_rules` 不同時出現。除了 `id`、`pack_key`、`enabled`、`notify` 之外的欄位都換成
  `pack_rules` 的值（`name` 也還原成空字串），確認後才換，換完還要按儲存。前端做，不加後端路由。
- 「試算最近 24 小時」：現有 `alert_rules.preview`。
- 刪除：編輯時在按鈕列左邊，沿用現有的兩段確認【判斷：舊頁的刪除在編輯頁，表單搬到這頁，刪除跟著搬，列上不放】。
- 狀態只有一份：表單打開某條規則時，列上的三段切換和表單裡的是同一個值，改哪一個都會讓另一個跟著變（列上的照舊立刻存）【判斷】。
- 儲存：送出前重新取規則清單。這條規則除了 `enabled`、`notify` 以外和表單打開時不同（別人或另一個分頁改過）時不送出，
  寫「這條規則在你編輯時被改過」並提供重新載入；相同時用最新的 `revision` 送出表單的整條規則【判斷：避免默默蓋掉別人的修改，
  也不讓列上切過狀態造成假衝突】。
  新增的回應不帶新規則的 id：用建立前後的 id 差找出新的那條，捲到它並短暫標示。

### 4.4 事件條件【樣張】

```
事件類型  (全部事件) (挑選事件)
          [user.sign_in ×] [user.login ×] [^agent\..* ×〈樣式〉]
┌ 分類 ─────────┬ [搜尋全部 294 種事件…] [全部動作|新增|修改|刪除|其他]  □ 隱藏已有規則的事件 ┐
│ 全部分類   294 │ ── rule_set · 3 種 · 政策 ─────────────────── □ 這組全勾            │
│ 已勾選       2 │ □ rule_set.create  當建立 Rule Set 時觸發。      已有規則：Rule Set 變更 │
│ ───────────── │ □ rule_set.update  …                                               │
│ 一般        13 │ □ ip_list.delete   當刪除現有的單一 IP list 時觸發。                  │
│ 政策     2/51  │                                                                    │
└───────────────┴────────────────────────────────────────────────────────────────────┘
事件等級  ☑ 資訊 ☑ 警告 ☑ 錯誤        結果 [成功或失敗都算 ▾]
▸ 更多條件：事件欄位比對、手動輸入事件類型（萬用字元、正規表示式）
```

- **全部事件**＝`event_types=["*"]`。
- **分類欄**：`alert_rules.event_catalog` 的 11 類，每類寫「已勾數／總數」；另有「全部分類」「已勾選」。≤ 720px 改成下拉選單。
- **搜尋**：比對事件類型、目錄說明、分類名稱；有搜尋字時不限目前的分類。
- **動作篩選**：事件類型最後一段是 `create`／`update`／`delete` 的歸三類，其他歸「其他」（294 種中 174 種是前三類）。
- **分組**：同一類裡，事件類型第一段相同的排在一起；兩種以上才有組標題與「這組全勾」。全勾存的是**當下列出的確切類型**，不是 `rule_set.*`
  【使用者採我的建議：條件欄看得到確切是哪些事件】。
- **已有規則**：事件被別的規則列出（確切類型，`a|b` 拆開算，`*` 與正規表示式不算；不論啟用與否，停用的寫「（停用中）」），該列寫
  「已有規則：{名稱}」，那條規則的結果不是全部時加「（只算失敗）」這類說明。照樣可以勾【使用者選 B】。點規則名稱關掉表單前先確認，然後打開那條規則。
  「隱藏已有規則的事件」只是篩選，已勾的不會被藏。勾了已有規則的事件，表單不帶入那條規則的設定【判斷】。
- **目錄外的類型**：規則裡不在目錄的類型（`a|b`、`*` 以外的萬用字元、正規表示式、PCE 新出的類型）一律以 chip 顯示並標「樣式」或「目錄外」，
  存回時原樣保留。輸入它們在「更多條件」的手動輸入框（現有 `EventTypesBox`），這個框只管目錄外的那些；目錄裡的由挑選區管。
  含逗號的樣式是一筆（`test_rule_form_acceptance_e2e.py:183`、`:207` 照舊）。
- **事件等級**：三個勾選框對應 `info`、`warning`、`err`。
  - 讀：`""`、`*`、`any`、`all`（`alertrules.py` 的 `_ANY`，不分大小寫）＝三個都勾；由 `info`／`warning`／`err`／`error`（`error` 是 `err` 的別名，
    `alertrules.py:183`）以 `|` 串成的值＝勾對應的幾個；其他（`!info`、正規表示式）勾選框換成文字框顯示原值【判斷】。
  - 寫：**使用者沒動勾選框就送回原字串**（`err|warning`、`error`、`*` 都不改寫）；動了才寫成 `all` 或 `info|err` 這種；都不勾不能存。
- **結果**：成功或失敗都算／只算成功（`success`）／只算失敗（`failure`）。讀寫規則同事件等級：`_ANY` 的任一個都算「都算」，沒動就送回原字串，
  其他值換文字框。
- 事件等級與結果**只在有意義時顯示**：選「全部事件」、勾到目錄標了 `severity_filter`（等級）或 `status_filter`（結果）的事件、或目前值不是 `all`。
  不顯示時寫一行「所選事件只會有一種結果（等級），不必選。」【判斷：294 種中只有 12 種會分結果、11 種會分等級，其餘一律顯示只會讓人以為可以篩】。
- **欄位比對**（`match_fields`）在「更多條件」裡，沿用現有 `EventFields` 的那一塊。有值時預設展開。

  【判斷：不補的話這些值看不到也改不了，「更多條件」有值卻是空的】。任一有值時預設展開。

1. 狀態用三段「停用｜只記錄｜通知」，取代舊頁的兩個開關（§4.2）。
2. 活動那一行除了樣張畫的上次觸發與 7 天次數，還有已知次數、擋下次數、暫緩與重設、資料狀態，因為舊頁有（§4.2）。
